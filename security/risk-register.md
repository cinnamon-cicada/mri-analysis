# Risk Register — The Brain Benchmark Project

Methodology: [NIST SP 800-30](https://csrc.nist.gov/pubs/sp/800/30/r1/final) (Guide for Conducting Risk Assessments), adapted to the size of this project — a solo-maintained research tool, not an enterprise deployment. This table was authored directly from a code/infra review (see git history around this file's introduction) rather than run through the browser-based [Open Risk Register](https://openriskregister.org) tool; that tool is a fine option if you want to maintain this interactively going forward — it implements the same SP 800-30 workflow and exports JSON/PDF, and your data never leaves the browser.

Likelihood / Impact: Low / Medium / High. Risk level = combination of the two, not a strict product.

Review cadence: revisit this register whenever a new endpoint, data flow, or GCP resource is added, and at minimum quarterly.

| R1 | Static, long-lived `service-account-key.json` (mri-api-sa) on developer disk. If leaked (laptop compromise, accidental commit, wrong `chmod`), grants Datastore User + Storage Object Creator on the whole project. | Medium | High | **High** | Gitignored via `*key*` pattern in `.gitignore`; not required for `STORAGE_BACKEND=local` dev | Rotate periodically; prefer Workload Identity Federation over static keys wherever the caller supports it (e.g. CI); add gitleaks to CI as defense-in-depth beyond `.gitignore` (see Track A.3) | Open |
| R2 | No PHI-scrubbing/defacing step in the FastSurfer pipeline. Full-head T1w NIfTI volumes are face-reconstructable — published defacing-benchmark work found success rates in the 80s-90s% for identifying a MRI-reconstructed face against a photo. `legal/privacy-policy.md` §3 calls this data "sensitive personal data" under GDPR Art. 9/HIPAA. | High (every upload) | High | **High** | `backend/deface.py` runs `pydeface` on the staged file before FastSurfer/storage ever see it, and the persisted upload is replaced with the defaced bytes (see `infra/Dockerfile.worker`) | Verify defacing doesn't degrade FastSurfer segmentation accuracy on a sample of real scans (defacing only touches face/ear voxels, but worth confirming empirically) | Mitigated |
| R3 | `infra/firestore.rules` / `infra/storage.rules` are deny-by-default and read correctly on manual inspection, but have no automated tests. A future edit could silently weaken them with nothing in CI to catch it. | Low (infrequent edits) | High | **Medium** | Rules are simple and reviewed by inspection | Add `@firebase/rules-unit-testing` suite against the Firebase emulator, run in CI (Track A.4) | Open |
| R4 | No audit trail for failed auth attempts or unauthorized job-access attempts — `backend/auth.py`/`app.py` only `print()`, which isn't durably captured anywhere. A breach or credential-stuffing attempt would leave no forensic record. | High (silent today) | High | **High** | None | Structured logging → Cloud Logging (Track B.1); Data Access audit logs on GCS/Firestore (Track B.2) | Open |
| R5 | No dependency, secret, or static-analysis scanning anywhere — zero CI existed before this work. | High (any commit) | Medium | **Medium** | `.gitignore` blocks the most obvious static-key commit pattern | `pip-audit`, `gitleaks`, `bandit` in CI (Track A.3) | Open |
| R6 | `legal/privacy-policy.md` §9 promises breach notification "within 72 hours." No detection capability exists to even learn about a breach that fast, let alone investigate scope and notify. This is a live commitment with no operational backing. | Medium | High | **High** | None | This entire plan (Tracks A–C), specifically the IR plan's 72-hour trigger (`security/incident-response-plan.md`) | Open |
| R7 | `backend/utils.py` builds `docker run` / `run_fastsurfer.sh` commands via `subprocess.run(list, ...)` (no `shell=True`). Static analysis (bandit) will flag subprocess usage generically. | Low | Low | **Low — accepted** | Args are a fixed list, not shell-interpolated; the only variable component (`subject_id`) is derived from `job_{uuid4()[:8]}`, not raw user input | None needed; document the bandit finding as a reviewed false-positive/accepted risk rather than suppressing silently | Accepted |
| R8 | `/status/{job_id}` and `/results/{job_id}` have no rate limiting (only `/upload` does). UUIDv4 job IDs are infeasible to brute-force (122 bits of entropy), but there's no throttle on lookup attempts, which is a minor DoS/enumeration-noise surface. | Low | Low | **Low** | `slowapi` limits now applied: 30/min on `/status`, 20/min on `/results`; UUIDv4 entropy makes brute force impractical regardless; ownership check via `_authorize_job_access` for signed-in users' jobs | None outstanding | Mitigated |
| R9 | GCS bucket and Firestore Data Access audit logs are off by default (only Admin Activity/System Event are on).
