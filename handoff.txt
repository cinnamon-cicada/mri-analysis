## REVISION NOTE 2

Two more developments since REVISION NOTE below:

1. BUG FIX: `./bin/run_app.sh` was throwing a 500 on every request to `/`
   ("TypeError: unhashable type: 'dict'" inside Jinja2's template cache
   lookup). Root cause: backend/app.py:38 called the OLD Starlette
   Jinja2Templates signature — `TemplateResponse("home.html", {"request":
   request})`. The installed Starlette build (1.3.1, pulled in
   unpinned as a FastAPI transitive dep — see CAUTION below) changed the
   signature to `TemplateResponse(request, name, context=None)`. Called
   the old way, "home.html" was bound to the new `request` parameter and
   the context dict was bound to `name` — Jinja2 then tried to use that
   dict as part of a cache key and blew up on hashing it. Fixed to
   `templates.TemplateResponse(request, "home.html")`. This was a latent
   bug (not a regression from this session's other edits).

   CAUTION for next session: requirements.txt pins `fastapi>=0.110.0`
   with no starlette pin. That is how a breaking Starlette API change
   reached this repo silently. Worth pinning starlette explicitly (or at
   least pinning fastapi to a tighter range) so a future transitive bump
   doesn't reintroduce this class of bug undetected — there is currently
   no test that exercises `GET /` and would have caught this before it
   hit the user as a live 500.

2. NEW UI/PRODUCT REQUIREMENT, stated directly by the user: the frontend
   is not actually a single page. It's three routes sharing the FastAPI
   backend:

   - `/self` — account creation and management. Redirects to `/login` if
     the visitor isn't signed in. Per-user stored data:
       - auth basics (whatever the chosen auth scheme needs)
       - email
       - brain-region statistics: "a one-layer JSON file" (i.e. a flat
         map, no nesting) populated after a successful MRI upload
       - benchmark results: map of {brain segment: percentile}
   - `/home` — file upload (this is the existing frontend/home.html
     upload flow; it just needs to move off `/` and onto `/home`, with
     `/` presumably becoming a landing page or a redirect).
   - `/data` — population statistics: a short blurb, then an interactive
     graph with a dropdown to pick a brain segment, plotting the COUNT
     DISTRIBUTION (a histogram, not a single percentile line) of values
     for that segment across the reference population.

   None of this exists yet. Concretely, today:
     - app.py only serves one route (`/`) rendering home.html — no
       `/self`, `/login`, `/home`, or `/data` routes.
     - There is no user/account model anywhere (storage.py's "jobs" are
       anonymous, keyed by job_id, not by user) and no session/auth
       middleware at all — zero auth infrastructure exists in the repo
       today, not even a stub.
     - There is no endpoint that returns a histogram/distribution over
       backend/benchmark/HCP_YA_ALL.csv for a given segment — analysis.py
       currently only computes a single subject's percentile against that
       CSV, not the population's binned distribution.

   OPEN QUESTION — flagging before anyone builds this, not deciding it
   here: this repo is already a registered Firebase project (Firestore +
   Storage are wired up per CLAUDE.md's GCP Infrastructure section).
   Rolling a custom password/session auth system from scratch for `/self`
   would mean owning password hashing, session/cookie security, and
   token refresh — real attack surface — when Firebase Authentication
   (email/password or OAuth) is a few lines of client SDK plus verifying
   the ID token server-side, and reuses infra that's already provisioned
   and billed for. Recommend Firebase Auth over a hand-rolled scheme
   unless there's a concrete reason it doesn't fit (e.g. needing to run
   fully offline/local-only with no Firebase project at all) — the user
   should confirm before Phase work starts on `/self`.

## REVISION NOTE

This document was regenerated after two developments not reflected in the
original version:

1. Phase 1 code fixes (1a-1g below) were already committed since the
   original handoff was written. They are kept here for the record,
   marked DONE, with commit hashes.

2. New product requirement, stated directly by the user (not previously
   documented anywhere): uploads are held until one of TWO concurrent
   FastSurfer processing slots is free; UP TO FIVE files may be stored
   (queued + processing) at once; the 6th+ upload must be rejected with
   a toast: "Please upload later due to reaching server capacity."
   Nothing in the codebase or original plan implemented this.

   Working through this requirement surfaced a deeper problem: the
   original plan (Phase 1d, already committed as cd551d1) deploys the
   worker as a Cloud Run SERVICE reached via Cloud Tasks HTTP dispatch.
   Cloud Run Services have a hard, non-negotiable 60-minute request
   timeout. The user has confirmed FastSurfer runs can take "many hours"
   per subject — a Service can never complete that request; it will be
   killed mid-run every time. This is not a config/timeout-value problem,
   it's a wrong-primitive problem.

   Decision (confirmed with user): move the worker to a CLOUD RUN JOB
   (supports up to 24h per task execution, no HTTP request involved) and
   drop Cloud Tasks entirely. Cloud Tasks' `max-concurrent-dispatches`
   only gates *outstanding HTTP calls*; starting a Job execution returns
   almost immediately, so once the worker stops being an HTTP endpoint,
   Cloud Tasks can no longer enforce "2 concurrent" — a Cloud Tasks task
   would look "done" the instant it kicks off a job that then runs for
   hours. The 2-slot rule now needs to be enforced by a dispatcher that
   watches actual job status in Firestore, not by counting in-flight
   HTTP calls.

   This affects Phase 1 (code), Phase 2 (GCP resources), Phase 3
   (placeholders), and Phase 4 (deploy) below — all rewritten.

PHASE 1j — DISPATCHER (NEW)
---
Replaces Cloud Tasks as the thing that decides "start the next job."
Enforces the 2-slot rule for real, based on actual job status, not
in-flight HTTP calls.

1j-i. New Cloud Function (2nd gen), e.g. backend/dispatcher.py, triggered
      on Firestore document writes to the "jobs" collection
      (`google.cloud.firestore.document.v1.written` Eventarc trigger,
      Firestore Native mode supports this natively).

1j-ii. On every trigger firing, in a Firestore TRANSACTION (required —
       two near-simultaneous writes must not both see "1 slot free" and
       both dispatch):
         a. Count docs with status == "processing".
         b. If count < 2: query the oldest doc with status == "queued".
            If one exists, set its status to "processing" INSIDE the
            transaction (claims the slot atomically), then outside the
            transaction call the Cloud Run Admin API
            `projects.locations.jobs.run` for job `mri-worker`, passing
            job_id/file_ref as container env overrides.
         c. If no queued doc or no free slot, no-op.
       This also self-drives: when a running job finishes and worker.py
       flips its status to completed/failed, that write re-triggers the
       dispatcher, which then picks up the next queued job. No polling
       or Cloud Scheduler needed.

1j-iii. New service account: mri-dispatcher-sa@PROJECT_ID.iam.gserviceaccount.com
        Roles: roles/datastore.user (transactional read/write),
               roles/run.developer (permission to call jobs.run).
